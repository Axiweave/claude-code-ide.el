#+title: Remote Agents and Project Views
#+options: toc:2 num:nil

* Purpose

Remote attachment connects Emacs to an existing zmx Session through SSH.
Attachment never starts a replacement Agent.
Explicit [[*Worktree Management][Worktree management]] can create Worktrees and launch Agents after confirmation.

The terminal path and the optional Project-view path are separate.
A Project-view failure does not detach or block the terminal.

For local persistent Sessions, see [[file:zmx.org][Persistent Sessions with zmx]].

* Requirements

Prepare these items outside Emacs:

- Install stock zmx on each remote host.
- For attachment, start the Agent inside an existing zmx Session.
- Configure SSH authentication, ports, jump hosts, and trusted host keys.
- Install Ghostel and its required native support.
- Add each exact SSH destination to =claude-code-ide-remote-hosts=.

Remote attachment supports Ghostel only.
The remote host does not need the Claude Code IDE Emacs package.
The local machine does not need a local zmx or Agent executable for remote attachment.

* Configure Hosts

List exact SSH destinations:

#+begin_src emacs-lisp
(setq claude-code-ide-remote-hosts
      '("my-agent-host" "user@another-host"))
#+end_src

The package never scans for hosts.
Remote discovery and control contact only the host that an explicit action selects.
An enabled Project view can connect only to an exact approved host when its attached Session first enters a managed layout.

The configured string can name an SSH configuration alias or =user@host= destination.
SSH configuration owns nondefault ports and jump hosts.
The package rejects blank, option-like, whitespace-containing, and control-character host values.

Remote control requests use batch authentication and strict host-key checking.
They cannot ask for passwords or accept a new host key.
Each control request has a 30-second total deadline and no automatic retry.

* Attach Existing Agents

Attach one remote Agent:

1. Run =C-u M-x claude-code-ide-attach=.
2. Select a Configured host.
3. Select an existing zmx Session.
4. Supply the Agent or remote directory if discovery cannot identify it.

The remote directory is metadata.
It does not need a matching local checkout.
The package never adds discovered commands or directory text to a remote launch command.

Use these commands for more Sessions:

- =C-u M-x claude-code-ide-attach-all= attaches every usable target on one host.
- =C-u M-x claude-code-ide-attach-select= opens a marked-selection buffer for one host.

Bulk attachment skips a target with an unknown Agent command or unusable directory metadata.
The result names each skipped target.
Individual attachment permits manual Agent selection and absolute remote-directory input.

Fresh attachment uses the discovery result.
Remembered reattachment first checks the exact target with =zmx list --short=.
Both paths use =zmx attach NAME false= as the final disappearance guard.

* Worktree Management

Worktree management adds explicit remote launch, creation, and lifecycle
operations beside the attachment above.
It targets one exact Configured host and one absolute remote repository
path, and it never scans a host for repositories.
See the [[file:../README.org::*Remote Worktree Management][Remote Worktree
Management section of the README]] for the manager =W= menu, the
=claude-code-ide-remote-launch-config= option, and the results-buffer
keys. This section covers the guarantees behind those commands.

The explicit manager open command always asks for a Configured host and a
repository. The repository picker shows recent paths only for that exact
host. Enter a new absolute path directly when it is not listed.

The manager records a path only after the request returns an operation ID.
Cancellation, invalid input, and refused requests leave history unchanged.
Restore validates and bounds stored text without local file checks or remote
requests. History for a removed host remains stored but cannot enter the
picker until that exact host becomes Configured again.

If an expected path is absent, first confirm that manager persistence is
enabled. Then confirm that the earlier request reached accepted operation
creation. Enter the absolute path directly to add it again.

** Preparation and Admission

Every mutation captures the exact host, repository, action, and
originating context first.
It re-verifies host approval before preparation and again before
dispatch.
It resolves Worktrees, branch identities, and executable paths on that
host, validates names and collisions before creating anything, and
queries fresh remote Agent inventory.
It then shows a confirmation naming the exact host, targets, and
consequences before it sends anything.
A declined confirmation makes no mutation.

Inventory accepts both =start_dir= and the zmx 0.8
=cwd=file://HOST/PATH= format.
URI paths decode percent escapes and UTF-8 without changing literal plus signs.
Encoded control characters, malformed escapes, and invalid UTF-8 remain unresolved.
Missing or malformed identity fields block protected operations.

Manager creation omits the initialization option when the Lane setting is disabled.
An explicit Lane initialization option on Worktrunk fails before mutation.

** Agent Bootstrap

Creation with Agent launch owns a generated zmx name and a unique
token before any request leaves Emacs.
The Agent runs inside an owned zmx wrapper.
That wrapper writes an ownership receipt in the private operation resource.
A name collision never runs a replacement command or stops the existing Agent.
Missing ownership proof leaves launch unverified.

Launch failure preserves an already-created Worktree.
Attachment failure after a verified launch preserves the Agent and
offers explicit attachment instead of another launch.
Reattachment reuses the same =zmx attach NAME false= guard used by
[[*Attach Existing Agents][existing attachment]].

** Agent Protection

Before removal, movement, history rewriting, or cleanup, Emacs runs a
fresh, bounded Agent-inventory check on the affected Worktree.
A running, detached, or idle Agent blocks the action.
Failed discovery, or an Agent whose affected Worktree cannot be
resolved, blocks the action too: absent local manager rows never imply
safety.
A merge check covers the source and the destination Worktree.

The action never stops a blocking Agent itself.
Stop it explicitly, then retry: the retry re-checks from scratch.
A force choice never bypasses this check.

** Results, Check Outcome, and Retry

Every operation stays in the local results buffer until Emacs exits,
even after its results window closes.
Check outcome is an explicit, read-only action against the exact
captured host and target.
It never writes, removes a resource, signals a process, starts an
Agent, or approves a hook.

Check outcome classifies each operation as completed, still running,
confirmed unfinished, partially completed, or still unknown.
An entered step without an exit receipt is =pending= only when fresh
evidence verifies that its worker still runs. Uncertain worker state
leaves that step =unknown=.
A matching directory, or a missing response, is never proof of
completion by itself.
Retry stays unavailable for an unknown or still-running step.
It can offer only a step Check outcome proved both unfinished and
safe, as a new mutation with its own confirmation, never a replay of a
completed or uncertain step.

** Cancellation and Observation

A remote mutation has no fixed execution deadline once dispatched.
Its pending state stays visible while other editor and terminal work
continues.

Cancel before dispatch prevents the mutation.
Cancel after dispatch stops local observation only: the remote
operation and its worker continue.
Closing the results view does the same.
Neither sends a remote signal, kills an Agent, removes receipts, or
closes a shared RPC connection.

A completed remote sequence can finish after observation stops.
The local completion handler does not steal focus, open a new view, or
attach a terminal after cancellation.
Check outcome can offer those actions later, explicitly.
A lost connection stops automatic observation without starting a
reconnect loop.

** Views After Directory Changes

Preparation captures the current remote directory and resolves its
Worktree identity on the selected host. This also covers Magit views
opened outside the Project-view registry.

When that directory disappears, completion opens a verified same-host
survivor only while the operation retains display ownership.
Unrelated navigation or cancellation leaves explicit recovery available.
When no Worktree survives, results report =Project view: unavailable=.
Edited file buffers remain intact.

Completion also refreshes safe existing survivor views when the origin
Worktree remains. It publishes fresh backend rows before native refresh.
Ordinary section rendering reads only the cached snapshot.
Edited or shared views retain their contents.

Retained, unmodified Magit and Dired views show an unavailable header with
the host and removed path. This includes known subdirectories of that
Worktree, but not sibling-prefix paths or paths on another host.
The feature preserves uncertain paths without resolving aliases.
It does not reuse unavailable views without fresh preparation,
even if another Worktree later uses the same path.

** Optional Dependencies

Remote creation and its Magit-driven follow-on actions need =magit-lane=
or =magit-worktrunk= loaded, with that backend's binary resolved on the
selected host.
Neither backend package requires =claude-code-ide= at load time; a
remote-aware backend command reports a missing package instead of
doing partial work.

Remote views opened by create-only or Magit actions need the same
optional =tramp-rpc= client as [[*Optional Project Views][Optional
Project Views]], currently Emacs 30.1 or later.
Remote listing, creation, and launch through the results buffer still
target Emacs 28.1 or later without that client.

** Operation Boundaries

The manager provides list, open, and create.
Backend lifecycle commands run from remote Magit through =magit-lane=
or =magit-worktrunk= when =default-directory= names an approved remote Worktree.
Native Magit move and push commands use capture before process creation
or native cleanup, then enter the same admission boundary.
Capture preserves destination interpretation, force flags, and resolved refspecs.
Unsupported command shapes fail without execution.
See [[file:../../magit-lane/README.org::*Remote Worktrees][the magit-lane
remote operation table]] and
[[file:../../magit-worktrunk/README.org::*Remote Worktrees][the
magit-worktrunk remote operation table]] for the exact behavior of each
action.
Lane never moves a Worktree, on any host, because it owns a fixed tree
location.
No backend moves a Worktree between hosts.

Worktrunk merge records landing and cleanup as separate steps.
Landing uses =wt merge --no-remove= toward the confirmed target.
Cleanup checks source identity, cleanliness, and Agent inventory again.
A new Agent can block cleanup without undoing or repeating landing.
An explicit retry can run only the proved, unentered remainder.
Invocation-only target overrides preserve existing Git environment entries
and never change persistent default-branch settings.

* Manager Lifecycle

Remote rows appear only in the global manager.
Each row identity includes the host and exact zmx name.
Matching project paths or zmx names on different hosts remain separate.

The manager uses these remote lifecycle keys:

| Key | Action |
|-----+--------|
| =RET= | Open a connected Session terminal. |
| =c= | Reattach a disconnected row explicitly. |
| =D= or =X= | Detach and remove the local row without stopping the Agent. |
| =K= | Confirm and Stop the exact remote zmx target. |
| =R= | Reset the Session layout to the selected preset and retry its companion. |
| =? C= | Cancel the pending Project-view attempt. |
| =? m= | Refresh cached Git metadata for one Configured host. |

Selecting or refreshing a disconnected row never contacts its host.
Startup and layout restoration never reconnect automatically.
A successful reattach keeps the Session ID, title, order, pin state, and saved layout.

Closing a remote terminal buffer detaches the local client.
The manager retains the row as disconnected.
Output silence alone does not prove disconnection or Agent completion.

Stop sends one remote kill request after confirmation.
The package requires the exact zmx acknowledgment and a separate absence check.
An ambiguous result keeps the row and does not retry the kill.

A shell preset's companion is an ordinary Ghostel shell, not a Project view.
Ordinary reattachment, restoration, and navigation reuse a live owned shell but never start or replace one.
=R= is the only action that can start a replacement shell, and only when no live shell remains.
Detach (=D= or =X=) and Stop (=K=) release the manager's ownership record without closing a live shell, its process, or its connection.

* Remote Git Metadata

Attachment can request read-only Git metadata asynchronously.
A metadata failure does not undo attachment.

The metadata request uses only =cd=, =git rev-parse=, and =git symbolic-ref=.
It creates no remote files.
It rejects control characters and malformed response paths.
A malformed response rejects the complete batch and preserves the last valid cache.

Manager =? m= refreshes metadata for known rows on one selected host.
It does not discover, attach, reconnect, or Stop an Agent.
Ordinary manager =G=, startup, restoration, navigation, and redraw make no metadata request.

* Optional Project Views

Remote layouts support six presets: =magit-left=, =magit-right=, =dired-left=, =dired-right=, =shell-left=, and =shell-right=.
They place a Git view, direct Dired buffer, or ordinary Ghostel shell beside the existing Agent.
All three share the same preparation worker, the installed =tramp-rpc= client, and its configured remote server.
The optional client currently requires Emacs 30.1 or later.

Install and configure the client and server separately.
This package never downloads, builds, installs, transfers, deploys, or updates either component.
It preserves the client's global and saved configuration.

Enable Project views for exact hosts:

#+begin_src emacs-lisp
(setq claude-code-ide-remote-hosts '("my-agent-host")
      claude-code-ide-remote-project-view-hosts '("my-agent-host")
      claude-code-ide-remote-project-cleanup-hosts nil)
#+end_src

A host must occur in both the access list and the Project-view list.
The Project-view list does not grant remote access by itself.
Changing either option starts no connection or window change.

This same two-list admission covers every preset, including both shell presets.
Preset selection never adds a host to either list.

** Preparation

The first managed display shows the terminal before it starts Project-view preparation.
Preparation runs in a worker and keeps the terminal interactive.
On macOS, a temporary timer gives the worker execution time while the GUI is idle.
The timer stops when the worker exits.

Each fresh worker requires a current RPC health response.
The health phase has a 30-second feature deadline.
A failure reports the host, phase, and corrective action while it retains the terminal.

Preparation captures the preset, companion kind, provider, exact Session directory, companion side, and shell creation permission.
An explicit reset supersedes the older request. A stale result cannot control a newer layout.

For a Git-based preset, the default provider opens Magit for a Git Worktree.
It falls back to Dired for a non-Git directory or unavailable Magit.
The existing =claude-code-ide-manager-status-buffer-function= remains authoritative and receives the RPC-qualified Session directory.

For a Dired preset, preparation opens Dired directly for the exact requested Session directory.
It never calls the configured Git provider and never substitutes a Magit buffer.

For a shell preset, preparation creates or reuses one ordinary Ghostel shell for the Session in its exact requested directory.
Shell creation uses the Session helper, not the shared Project-view registry.
It follows the installed RPC client's PTY policy and Ghostel's remote shell preferences.

** Identity and Reuse

Project-view identity includes the exact host, canonical Worktree or directory, companion kind, captured provider object, and requested directory.

This identity governs only Magit and Dired views.
Distinct provider objects remain separate even when their Lisp representations compare equal.
A Dired request never reuses a cached Magit buffer, and a custom Git provider never reuses an unrelated Magit view.

Ordinary Session reuse keeps a matching buffer without a refresh.
Explicit Worktree refresh and recovery refresh safe native views.
Recovery rejects a native view if its current host or directory no longer matches its registered identity.
It preserves views with uncertain native state, temporary files, or unknown local kill or query hooks.
Fresh preparation checks unavailable native views before the provider can reuse them.
It refuses reuse when edits, shared ownership, or uncertain state require preservation.
Remote Worktrunk marks the current row from each view's directory, not the shared snapshot's original query.
Use the view's native =g= command for other manual refreshes.

Bulk attachment does not prepare every project.
Each Session starts preparation only when its managed layout first appears.

A companion shell uses a separate ownership model from Magit and Dired views.
Each Session owns at most one live shell, tracked by its exact Session ID rather than by directory, Worktree, host, or buffer name.
Different Sessions in the same directory never share a shell.
Reset to a shell preset reuses that Session's live owned shell without a new RPC connection.
Only an explicit reset starts a replacement, and only when no live shell exists.
A shell from a superseded or no-longer-current request stays alive as an ordinary terminal.
It never joins the shared Magit/Dired registry above and is never adopted into a newer request.

** Dismissal, Reset, and Cancellation

Closing a Project-view window suppresses automatic display for that Session.
The suppression survives navigation and remote reattachment during the current Emacs process.
Other Sessions that share the buffer keep their own display intent.
An ordinary manager switch, including a switch to a local Session, does not suppress the view.
Returning to the remote Session displays its ready Magit or Dired view even without a saved layout.
Ordinary return never starts or replaces a companion shell.
It preserves retained output and shows reset guidance when the shell has exited or is missing.

Press manager =R= to clear that Session's suppression.
This command resets the layout to the configured preset.
Git, Dired, and new shells use fresh health-gated preparation.
It does not restart the Agent.
A live owned shell returns without a worker, health check, or new connection.

Open the manager menu with =?= and press =C= to cancel a pending attempt.
Cancellation blocks stale results from changing a newer Session or attachment.
It does not detach the terminal or close a shared RPC connection.

** Optional Cleanup

Enable cleanup independently for exact hosts:

#+begin_src emacs-lisp
(setq claude-code-ide-remote-project-cleanup-hosts
      '("my-agent-host"))
#+end_src

Cleanup runs only after a successful manager =D= or =X= detach.
It can close only an unmodified Magit or Dired buffer that this feature created for that detached Session.

Cleanup retains reused, custom, modified, shared, source-file, process, temporary, replaced, and uncertain buffers.
It also retains buffers with unknown local kill or query hooks.
Cleanup never saves, prompts, makes a remote request, or closes an RPC connection.

Terminal close, network loss, Stop, and Emacs exit do not run Project-view cleanup.

Cleanup never applies to a companion shell.
Confirmed removal releases the shell ownership record without closing the shell buffer, process, or connection.
Temporary disconnection preserves ownership for explicit reattachment.
See [[*Manager Lifecycle][Manager Lifecycle]] for the exact shell-survival rules.

* Scope Limits

Remote mode does not provide these features:

- Automatic Agent replacement for a missing or failed attachment.
- Automatic reconnect.
- Remote host discovery.
- Remote Treemacs actions or project launch commands.
- Text transfer to the remote Agent.
- MCP or SSE setup for the remote Agent.
- Structured Agent state from the remote process.

Remote Sessions use terminal-output activity and output-idle detection.
Output idle does not mean that the Agent completed successfully.

* Troubleshooting

** Authentication fails without a prompt

Test the same SSH destination outside Emacs.
Configure noninteractive credentials and accept the host key before you use remote mode.

** The host reports that zmx is missing

Make =zmx= available in the remote command environment's =PATH=.
The local =claude-code-ide-zmx-program= option does not control the remote executable.

** Ghostel or its native support is unavailable

Install Ghostel and its required native support, then retry.
The check happens before Emacs starts a terminal or SSH attach process.

** A disconnected target cannot reattach

Run =zmx list --short= on the selected host.
Restore the exact target or remove its local history with manager =D= or =X=.
The package never creates a replacement Agent.

** The terminal works but the Project view fails

Read the phase in the host-qualified error.
Check the installed client, noninteractive authentication, remote server path, remote directory, or provider for that phase.
Then press manager =R=.

** A Project view does not return after navigation

Ordinary manager navigation preserves the Session's view.
If you closed its Project-view window, press manager =R= to clear suppression and rebuild the default layout.

** Root cause: macOS GUI worker starvation

The September 2026 investigation used Emacs 31.1.50 with the native macOS =ns= GUI.
After detach, attach, and =R=, the terminal could remain alone while Project-view preparation stalled or reached its 30-second health deadline.
Batch tests passed, and =emacsclient= queries sometimes made the same attempt complete.

*** Mechanism

The native GUI can keep Emacs's global Lisp lock while its main thread waits inside =[NSApp run]=.
In =src/nsterm.m=, =ns_select_1= briefly calls =thread_select= before it returns to that native event loop.
An unrelated timer, input event, or eligible process descriptor can wake the main loop.
Without an explicit yield, those wakes do not guarantee that a worker acquires the Lisp lock.

In =src/process.c=, =compute_input_wait_mask= excludes descriptors that belong to another thread.
The former =claude-code-ide-remote-project--call-rpc= advice assigned the shared RPC transport to the worker with =set-process-thread=.
That ownership also prevented the transport's response from waking the main loop.
Unlocking the process alone was insufficient: the main thread could receive the response without letting the waiting worker resume.

*** Why the first fixes and checks misled us

A global RPC mutex serialized workers but did not release the main thread's Lisp lock.
The RPC client already matches responses by request ID, so the mutex added contention without fixing the stall.
An available response in the connection's table did not prove a response-ID collision.

Diagnostic timers and =emacsclient= requests introduced the main-loop activity that the idle reproduction lacked.
Cursor blinking could also change the result.
A batch test did not exercise the native GUI event loop.
The old tests asserted process ownership and mutex serialization rather than useful progress, so they gave false confidence.

*** Repair and lifetime rules

On an =ns= build, =claude-code-ide-remote-project-prepare= starts a main-thread timer that calls =thread-yield= every 0.05 seconds.
The timer starts before =make-thread= and remains active until that worker exits.
It must continue after health succeeds, through Magit preparation and any deferred connection cancellation.
The worker's outer =unwind-protect= cancels the timer.
If worker creation fails, the main thread abandons the attempt and cancels its timers.
Idle Sessions retain no scheduler timer.

The repair removes the per-call process-ownership advice and the global mutex.
The connection and server-start guards still release transport locks that the creating worker owns.
They retain the existing admission, cancellation, and no-deployment checks.

*** Verification evidence

A controlled GUI probe disabled cursor blinking and used a worker with a local =cat= pipe.
The worker sent 20 messages and waited with =(accept-process-output process 0.05 nil t)=.
Without a yield timer, the worker did not start before the 12-second safety timeout.
A timer that only called =ignore= did not reliably restore progress.
With the yield timer, an independent run completed all 20 exchanges in about 0.06 seconds.

Two live cold detach, discovery, attach, and =R= runs displayed Magit after =R= in 0.42 and 0.61 seconds.
Those runs disabled cursor blinking and used no diagnostic sampling timers.
The final check also required populated Magit status sections, not just a buffer name or a =ready= flag.

For future regressions, test the idle native GUI as well as batch ERT.
Check the exact Session, both visible windows, valid status sections, and scheduler cleanup.
If the yield timer runs but the response table stays empty, investigate the RPC connection separately.
The investigation also found an unresponsive connection that timed out on native =system.info= and recovered after native-client cleanup.
Do not treat every later health timeout as this scheduling defect.

The feature deadline starts before the native client's per-request timeout.
It can abandon an attempt before native timeout cleanup retires an unresponsive connection.
Repeated =R= attempts can then reuse that stale connection.
This remains a separate timeout-ordering risk.
The scheduling repair preserves the specified 30-second health deadline and does not change the native client's timeout policy.
